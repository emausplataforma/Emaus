=========================================================================================
2. AUTENTICAÇÃO EM DOIS FATORES
=========================================================================================

  Configurações e segurança ▸ cartão 2FA

    · Desligada  → botão Ativar
    · A API gera uma chave TOTP (SHA-1, 6 dígitos, janela de 30 s ± 1)
    · Você cadastra a chave no autenticador (Google Authenticator, Authy…)
    · Confirma o código de 6 dígitos → 2FA Ativa
    · Aparecem 8 códigos de recuperação, uma vez só. Guarde. Cada um vale uma vez.
    · Para desligar: o código do autenticador (ou um de recuperação)

  O segredo NÃO fica em texto no banco: AES-256-GCM, chave derivada de JWT_SECRET.
  A chave da tela some depois de confirmar. Não tem como a interface “preparar”
  o 2FA sem você confirmar o código.

  Login do administrador, quando o 2FA está ativo:

    1. e-mail + senha
    2. a API devolve um ticket de 5 minutos (ainda sem token)
    3. aparece o campo “Código 2FA ou de recuperação”
    4. só então entra

  Rotas novas (server.js — precisa ir para o Railway quando você mandar publicar):

    POST /api/auth/login/2fa
    POST /api/me/security/2fa/start
    POST /api/me/security/2fa/confirm
    POST /api/me/security/2fa/disable
    GET  /api/me/security   → { twoFactor, database }

3. POSTGRESQL — CONECTADO DE VERDADE
=========================================================================================

  O cartão deixou de se chamar “Backup PostgreSQL”. Backup do provedor a tela
  não vê, e não vamos inventar snapshot da Railway.

  O que ela faz: SELECT NOW() e a versão do servidor.

    · Conectado  → versão (ex.: 16.4) e o tempo da ida-e-volta em ms
    · Indisponível → a API não alcançou o banco neste instante
    · Verificar agora → ping de novo

  O mesmo selo aparece no resumo da Visão geral, no lugar da linha
  “Backup PostgreSQL / Não verificado”.
